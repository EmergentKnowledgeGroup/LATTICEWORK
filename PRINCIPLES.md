# Principles

## 1. Preserve value before replacing structure

The upstream system contains ideas, behavior, and user value that deserve honest characterization. Reengineering begins with understanding, not deletion.

## 2. Context is not architecture

Context can explain a system. Architecture lets the system explain itself.

## 3. Compaction is lossy, so design for bounded loss

LATTICEWORK does not claim that compaction is perfect. It claims that critical truth should live in code, tests, schemas, decisions, and state documents rather than only in an active conversation.

## 4. Local truth for local work

A contributor changing one component should not need the entire repository history in active memory. Interfaces and invariants should define the necessary local truth.

## 5. No receipt, no claim

Every public claim must point to pinned source, a command, an artifact, a test, or an independently reproducible observation.

## 6. Compatibility is behavioral

Matching names, screens, or line counts does not prove compatibility. User-observable behavior, stored data, integration contracts, and failure behavior matter.

## 7. Smaller is not automatically better

Line count, file count, and dependency count are measurements, not verdicts. The project optimizes for navigability, correctness, change safety, and user value.

## 8. Explicit boundaries beat implied relationships

Services, modules, schemas, interfaces, and ownership boundaries should be named and testable.

## 9. Tests are durable memory

A passing test is not perfect truth, but a missing test is a forgotten promise waiting to become a regression.

## 10. Documentation must match reality

A beautiful architecture document that describes code that does not exist is worse than no architecture document.

## 11. Handoffs are engineering work

Every interrupted session should leave a clear current state, evidence trail, unresolved risk list, and next action.

## 12. Attribution is non-negotiable

Upstream history, license, and worthwhile contributions remain visible. Distinct identity does not require erased provenance.

## 13. Critique the work, not the worker

The project can be devastatingly clear without becoming personally abusive.

## 14. Be willing to be wrong

LATTICEWORK should correct its own measurements, claims, and architecture as aggressively as it corrects upstream problems.

## 15. The repository is the argument

The strongest public statement is software that third parties can inspect, run, test, and improve.
